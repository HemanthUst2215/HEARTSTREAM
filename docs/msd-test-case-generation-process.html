1. Inputs used

Runtime generation reads stored rulebooks and a user story workbook (typically produced right after story generation from a workshop transcript). A sample E2E execution plan is used only once to define the MSD rulebook—it is never opened during generation.

📄

User Story Excel

Standard story export layout. Rows include Epic, Feature, and User Story work items with Description and Acceptance Criteria.

📖

MSD test case rulebook

Sheet names, columns, test case ID pattern, case model, allowed values, and generation logic—the permanent layout contract.

📝

Source story rulebook

Defines how to find the header row and which column is User Story. Used only for extraction—not for rewriting stories.

⚠

Intake safety

The story workbook is untrusted intake: it is scanned for injection and sensitive data before any extraction or authoring.

Bootstrap vs runtime

  • One-time Sample E2E execution plan → MSD rulebook via rulebook bootstrap authoring.
  • Every run Agents load the stored rulebook only. Layout and patterns are configuration, not copied sample rows.
  • Never Read bootstrap cell content, ISV product lists, or process names into generated cases.

3. Generation flow

Plan → Act → Observe → Reflect (up to three iterations). The first pass that clears validation is enough to stop. Human gates: intake safety, output conflict resolution, and review of the delivered workbook.

Mechanical vs agent-owned

  • Automation — Header discovery, story filtering, workbook rendering, coverage and ISV derivation, validation.
  • Agents — Grouping notes, positive and exception case selection, step text from cited acceptance criteria, test data only when cited, open questions when exception evidence is missing.
  • Agents must not — Hand-edit the workbook, add columns, invent Dynamics modules or failure paths, or produce sprint markdown test catalogs.

4. Case model per scenario

Each scenario group gets at most two test cases: one happy path and one exception or control path—only when the stories evidence constraints, negatives, or boundaries.

Positive case

Test type: Positive E2E. ID polarity: P (for example scenario 01, positive 01). Built from happy-path acceptance criteria and the story need and benefit.

Exception / control case

Test type: Negative or Control, or a more specific negative class when AC names it. ID polarity: N. Omitted when there is no cited failure or constraint—log an open question, do not invent.

flowchart LR G[Scenario group] --> P[Positive E2E case] G --> N[Exception case if evidenced] P --> S1[Happy-path steps] N --> S2[Constraint steps]

Automation sequence (every run)

  • Extract stories from the user story workbook into a story snapshot.
  • After agents author cases, write the case row set and render the E2E workbook.
  • Run the compliance validator and keep reflecting until it passes.

7. Artifacts & definition of done

Outputs are versioned under intake storage plus a governance audit. Only the Excel package is the primary operator deliverable.

Story snapshotInternalExtracted stories and grouping keys

Extraction notesInternalScenario table, provenance, open questions

Command auditGovernanceWhat, why, validation, next step

Done when

  • Intake safety cleared (or documented waiver).
  • Output path gate cleared or explicit human overwrite.
  • Workbook validator reports pass.
  • No bootstrap execution-plan cell content in generated cells.
  • Audit written; harness updated for this phase-changing command.

8. End-to-end pipeline

Test case generation sits after user-story intake. It does not replace sprint test-package expansion (BR-linked catalogs and human approval before automated test runs).
